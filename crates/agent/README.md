# Rust agent

The agent currently provides device identity and mutual approval, an authenticated encrypted TCP session, a bounded four-service multiplexer, and capability-rooted Shared Workspace RPC. The multiplexer gives input, window video, extended-display video, and files independent service channels over one session. It prioritizes input and interactive video, applies bounded queues, and reserves periodic file progress. The desktop consumes the file channel; input and media producers/receivers are not integrated yet and must still report inactive.

The authenticated handshake and four-service frame format are protocol version 5. Version 3 added an explicit pairing-versus-trusted-reconnect discriminator; version 4 adds event-time screen coordinates to wheel input frames; version 5 adds the JPEG window-frame codec used by the consent-gated desktop receiver preview. Peers must run compatible builds. Older protocol versions are rejected during handshake validation rather than being interpreted as the new format. The preview has no connected capture producer or interaction forwarding and does not count as an interactive portal.

The agent also exposes a typed input-session contract and `InputSessionController`. The controller combines the ownership map with the ordered encrypted sender, leaves local-owner events for the local path, and routes only paired-remote-owner events to the input lane. Key/button release stays with the owner that got the original down. Native-to-session conversion preserves event-time coordinates and extended-key/horizontal-wheel metadata. The controller is not yet connected to ownership-aware global input capture, an explicit consent UI, or receiving-side native input injection. Raw Input does not suppress local OS delivery, so this contract alone does not redirect input or complete shared control.

The window and extended-display video lanes now have a typed encoded-frame envelope with session/device binding, codec, stream ID, sequence, source timestamp, dimensions, key-frame flag, and payload. Metadata uses a bounded JSON header while media bytes remain binary, avoiding per-byte JSON expansion. It rejects malformed/oversized frames, wrong destinations, replay/reordering, and invalid dimensions while allowing sequence gaps caused by stale-frame drops. Producers enqueue lossily under queue pressure so video cannot block the session. Capture, encode/decode, render, consent, and desktop lane consumers are not implemented.

Tests cover all four service channels over an in-process authenticated encrypted stream, Shared Workspace RPC over the multiplexed file channel, input and media frame validation, binary media payload round-trip, typed window/display frames transported alongside file-lane work, input ownership routing, bounded queues, bulk progress under input load, and cancellation cleanup. Physical LAN pairing, simultaneous input/video/file operation, and Windows acceptance remain unverified. Run `cargo test --workspace` from the repository root. Windows tests exercise DPAPI and filesystem behavior.
