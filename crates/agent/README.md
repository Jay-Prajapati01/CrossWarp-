# Rust agent

The agent currently provides device identity and mutual approval, an authenticated encrypted TCP session, a bounded four-service multiplexer, and capability-rooted Shared Workspace RPC. The multiplexer gives input, window video, extended-display video, and files independent service channels over one session. It prioritizes input and interactive video, applies bounded queues, and reserves periodic file progress. The desktop consumes the file channel; input and media producers/receivers are not integrated yet and must still report inactive.

The service frame format is part of protocol version 2. Both peers must run a build that supports the same protocol version. Old v1 clients fail the authenticated protocol-version check rather than misinterpreting a service tag as a file packet.

The agent also exposes a typed input-session contract. It sequences events over the encrypted input lane, binds them to a session and destination device, validates key/button down/up balance, synthesizes releases on disconnect, and uses the ownership router to send releases to the surface that received the original press. This contract is not yet connected to global input capture, an explicit consent UI, or native input injection; it does not suppress or redirect local OS input by itself.

The window and extended-display video lanes now have a typed encoded-frame envelope with session/device binding, codec, stream ID, sequence, source timestamp, dimensions, key-frame flag, and payload. Metadata uses a bounded JSON header while media bytes remain binary, avoiding per-byte JSON expansion. It rejects malformed/oversized frames, wrong destinations, replay/reordering, and invalid dimensions while allowing sequence gaps caused by stale-frame drops. Producers enqueue lossily under queue pressure so video cannot block the session. Capture, encode/decode, render, consent, and desktop lane consumers are not implemented.

Tests cover all four service channels over an in-process authenticated encrypted stream, Shared Workspace RPC over the multiplexed file channel, input and media frame validation, binary media payload round-trip, input ownership routing, bounded queues, bulk progress under input load, and cancellation cleanup. Physical LAN pairing, simultaneous input/video/file operation, and Windows acceptance remain unverified. Run `cargo test --workspace` from the repository root. Windows tests exercise DPAPI and filesystem behavior. Details: [input session evidence](../../docs/phase1-evidence/input-session.md) and [media session evidence](../../docs/phase1-evidence/media-session.md).
